Positional Base-N Compressor

Every character becomes a small code. All the codes fold into one big number through a single formula. That number, written in bytes, is the compressed message — and dividing it back apart rebuilds the text exactly. Watch each step happen below.

Step 1

Give each character a code

We scan the message and collect only the distinct characters it uses — that set is the alphabet. Its size is the base B. Each character gets a code from 0 to B−1. A smaller alphabet is the whole reason this can compress.

Step 2

Rewrite the message as codes

Now the text is just a list of code numbers — the digits of a number written in base B.

Step 3

The formula — fold every code into one number

Each code is a digit at its own place value. Add them all up and the entire message collapses into a single exact integer — the coefficient N.

Step 4

Store the number as bytes

Writing N in base 256 (raw bytes) needs only log₂(B) bits per character instead of 8. We add a tiny header — the alphabet and the length — so it can be decoded on its own. The base64 below is the compressed message.

Compressed message (base64)
Step 5

Decode — peel the digits back off

Take the number back apart with repeated divide and remainder by B. Each remainder is the next code; each code maps back to its character. No information is lost.

Reconstructed message
Step 6

Store it as an image

The compressed bytes are painted into pixels — three bytes fill each pixel's red, green and blue. Save the PNG and your message lives as a picture; load that PNG back and the engine reads the pixels, rebuilds the number, and recovers the text exactly. To anything but this engine it's just colored noise.

Why it can't compress everything (and can't run forever)

Compression here comes from one honest source: real messages use far fewer than 256 distinct characters, so each one fits in fewer bits. Text with a tiny alphabet (DNA, repeated strings) shrinks a lot; text that already uses many byte-values (random data, dense emoji) barely shrinks — or grows by the header.

And you can't feed the output back in to keep shrinking. Once the redundancy is gone there's nothing left to squeeze — a second pass makes it bigger. No lossless method can shrink every input, because distinct messages need distinct outputs and there aren't enough shorter ones to go around (the pigeonhole principle).
